# FoodFlow 商业运营级架构与运维基线

**适用仓库：** Tony855/shaolafang  
**目标：** 在保持现有顾客点餐、服务员、后厨、收银及超级管理员 API 兼容的前提下，分阶段提高 SaaS 隔离、安全性、并发可靠性和可恢复性。

> 本文是工程基线与实施约束，不代表已完成第三方支付网关验签、Prometheus 指标、异地备份或生产灾备演练。上线前必须按实际供应商和部署拓扑完成验收。

## 1. 核心业务边界：订单、支付、退款、结算

现有订单与财务逻辑集中在路由和服务模块中，并已有金额精度、退款、收银结算、KHQR 生命周期和事务测试。下一步应先建立明确边界，再逐步搬迁实现，不应一次性重写现有 API。

### 必须保持的业务不变量

1. 订单价格由服务端读取菜单价格并计算；不能信任客户端提交的总金额、折扣或退款金额。
2. 金额统一采用整数最小货币单位或精确 decimal 运算；避免使用浮点数直接累计账款。
3. 订单状态变更必须校验当前状态，并在事务中锁定订单行；并发冲突返回明确的 409，而不是覆盖较新的状态。
4. 支付通知必须校验支付渠道签名、商户/门店归属、金额、币种、订单引用和渠道交易号。
5. 支付回调必须幂等：同一渠道交易号重复通知只能产生一次入账和一次订单状态转换。
6. 退款必须校验已支付可退余额；同一退款请求应使用幂等键，退款成功后保留不可变的审计记录。
7. 订单、支付、退款和结算相关写入应在一个明确的事务边界内完成；事务外再发送 Socket.IO 通知或打印任务，失败时使用可重试任务/Outbox 模式。
8. 不允许因打印机、Socket.IO 或外部支付服务短暂不可用而回滚已经确认成功的支付账务。

### 建议的模块边界

- `orders`：订单创建、菜品行、订单状态机、桌台状态。
- `payments`：支付意图、渠道回调验签、渠道交易号和支付状态。
- `refunds`：退款申请、审批、渠道退款和退款账本。
- `settlements`：收银交班、现金/电子支付汇总、差异核对。
- `ledger`：不可变的借贷/收支流水，所有财务报表从账本或经过核对的聚合数据读取。

迁移时保留现有 API 路径和响应结构，通过服务层适配旧路由；每一步都要有数据库集成测试和回滚方案。

## 2. 多租户隔离

### 授权规则

- 商户身份来自已验证的会话，不来自请求体、URL 或客户端可任意修改的 `X-Store-Id`。
- 门店身份由认证中间件绑定；服务员账号必须绑定其所属门店。
- 每个业务 SQL 都必须在授权范围内过滤 `merchant_id` 和/或 `store_id`；不能只在查询后过滤结果。
- 跨商户资源访问应统一返回 404 或 403，避免泄露其他商户资源是否存在。
- Socket.IO 房间必须由已验证的会话推导，不能允许客户端自行加入任意 merchant/store 房间。
- 后台导出、打印、备份、批量删除和退款接口同样需要租户范围约束。

### 回归测试矩阵

至少覆盖商户 A 与 B、门店 A1 与 A2、不同角色（超级管理员、商户管理员、收银员、服务员、顾客）：

- 读取、修改、删除订单和菜品；
- 访问桌台二维码、预约、服务员、打印机；
- 下载报表、导出销售数据、读取审计日志；
- Socket.IO 订阅和事件广播；
- 退款、收银结算、转桌、重置数据；
- 篡改 URL ID、请求体 merchant_id/store_id、请求头门店 ID。

现有测试包含门店范围、管理员认证、Socket.IO 认证和退款/结算测试；每增加新业务接口，必须补充跨租户拒绝用例。

## 3. API 安全基线

- 所有管理端写操作必须经过认证和细粒度权限校验；仅登录成功不代表具备管理权限。
- 对登录、扫码会话创建、下单、催单、支付回调、导入和导出分别设置限流策略。
- 所有 SQL 使用参数化查询；动态表名/列名只能来自代码内固定白名单。
- HTML 输出使用统一转义函数；禁止把不可信数据拼入 inline script、HTML 属性或事件处理器。
- 上传文件检查扩展名、MIME、文件签名、尺寸和压缩后格式；上传目录不可执行。
- ZIP 导入必须防止路径穿越、符号链接逃逸、解压炸弹和资源耗尽。
- 认证 token 只通过 Authorization 或 Socket.IO auth 传递；禁止放在 URL query、访问日志和错误日志。
- 生产环境必须使用 HTTPS；CORS 使用精确来源 allowlist。
- `TRUST_PROXY` 只信任真实 Nginx/LB 内网 IP 或 CIDR，不能对公网使用 `true`。
- 错误响应不返回 SQL、堆栈、数据库地址、支付密钥或文件系统路径。

## 4. MariaDB 与并发性能

### 连接池预算

生产数据库统一使用 MariaDB 10.5+。集群总连接上限应满足：

`应用节点数量 × 每节点 DB_CONNECTION_LIMIT + 运维/迁移连接 < 数据库 max_connections`

必须为数据库复制、备份、监控和人工运维预留连接。不能仅提高应用节点连接池就宣称提升并发。

### 查询优化流程

1. 从慢查询日志或 APM 获取真实高频/高耗时 SQL。
2. 使用 `EXPLAIN ANALYZE` 检查扫描行数、索引命中、临时表和排序。
3. 按实际过滤条件建立复合索引，遵循最左前缀规则。
4. 大列表使用基于稳定唯一键的游标分页；避免无上限返回订单、审计日志和报表。
5. 报表使用有界时间范围、按日/门店聚合；必要时建立可重建的汇总表。
6. 每个新索引都要测量写入成本和存储开销；上线前先在备份/预发布数据库验证迁移时长。

### 事务规则

- 事务中只做数据库工作，不调用支付网关、打印机、HTTP API 或长时间文件操作。
- 多行锁定保持固定顺序，减少死锁；遇到可重试死锁时采用有限次数指数退避。
- 重要更新检查 affectedRows；不能把“SQL 没报错”视为状态已成功更新。
- 使用唯一约束和幂等键保护并发创建，而不只依赖应用层先查后写。

## 5. Redis 与多节点一致性

- 多节点环境必须共享同一受保护 Redis 服务；禁止依赖进程内 Map 实现跨节点限流、冷却或实时事件状态。
- Redis 连接必须使用私有网络和认证；生产环境优先使用 TLS。
- 对 Redis 不可用时的行为逐项定义：登录限流、下单冷却、Socket.IO adapter、幂等锁不能静默退化成不安全的每进程状态。
- Redis key 必须包含业务域/租户范围，并设置合理 TTL；禁止将支付密钥或明文 token 放入 key。

## 6. 健康检查、日志与告警

- `/api/health`：liveness，只确认 Node 进程仍能响应。
- `/api/health/ready`：readiness，确认数据库查询成功；数据库故障返回 503。
- Nginx `/health` 应代理到应用 readiness，不得由 Nginx 静态返回固定 200。
- 监控至少覆盖 HTTP 5xx、P95/P99 延迟、订单创建失败率、支付回调失败/重复率、退款失败率、DB 连接池等待、慢查询、Redis 连接状态、CPU/内存/磁盘和备份新鲜度。
- 日志采用结构化字段：request_id、merchant_id、store_id、actor_id、route、status、duration_ms；禁止记录密码、Authorization、完整支付 payload 和 token。
- 告警需要带有排障上下文和负责人；避免把每次重试都升级为独立告警。

当前新增 readiness 路由和部署健康检查；Prometheus exporter、APM 和告警接入仍需按实际监控平台另行实施。

## 7. 备份与灾难恢复

- 数据库备份应包含一致性快照和 Binlog/PITR（若数据库服务支持）。
- 自动备份文件应加密后复制到异地对象存储；备份目录权限不能替代加密和异地保存。
- 备份必须监控最近成功时间、文件大小、校验和及上传结果。
- 至少每季度在隔离环境执行恢复演练，验证订单、退款、商户、门店、管理员、配置和附件完整性。
- 恢复前确认目标数据库、版本兼容、备份校验和、停写窗口与回滚点。
- 任何恢复操作不得直接覆盖生产数据库；先在隔离库恢复并核对，再执行正式切换。

## 8. 发布与回滚

1. 通过 PR 合并，禁止直接在生产服务器编辑代码。
2. CI 必须通过语法检查、部署配置测试、租户隔离测试、财务测试和依赖审计。
3. 数据库迁移采用向后兼容的 expand/contract：先加字段/索引，再发布兼容代码，最后在确认无旧代码使用后清理旧字段。
4. 逐节点滚动发布；先摘除节点、部署、启动、执行 readiness 检查，再重新加入负载均衡。
5. 任一节点 readiness 不通过或错误率显著上升，应停止继续发布并回滚代码。
6. 数据库迁移若不可逆，必须先验证备份恢复点；不要把代码回滚等同于数据库回滚。

## 9. 本轮实际落地内容

- 修正标准版、企业版和旗舰版部署模板的数据库变量名称为 `DB_DATABASE`。
- 企业集群模板显式要求配置 Redis 和可信代理 IP/CIDR。
- 企业集群部署脚本在启动前验证数据库、Redis、可信代理配置，缺失时 fail fast。
- 企业集群升级流程拒绝覆盖本地未提交修改，并改用 fast-forward 更新。
- 修复集群数据库初始化脚本传入应用的环境变量名称。
- 新增数据库 readiness 接口；数据库异常时返回 503，且不泄露底层错误。
- Nginx 三种部署模板的 `/health` 改为代理 readiness。
- 修正静态资源正则转义。
- 健康巡检脚本改用部署配置中的 DB_HOST/DB_PORT/DB_USER/DB_PASSWORD/DB_DATABASE。
- 新增部署配置回归测试和数据库事务 AsyncLocalStorage 并发隔离测试。
