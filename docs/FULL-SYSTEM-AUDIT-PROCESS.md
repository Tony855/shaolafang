# 全系统功能完整审计流程

## 目标与执行原则

本流程用于对 FoodFlow / Shaolafang 的全部现存功能做可重复、可追踪、可验收的审计。它是全仓库审计基线，不代表任何模块已通过审计，也不以测试总数或覆盖率数字替代业务验收。

- 审计基线固定为本次执行时的 main SHA；PR 审计固定为最终 PR head SHA。
- 先盘点代码和现有证据，再测试；不按目录名推断功能已完成，不重复实现已有功能。
- 每项发现必须关联文件/路由/表/测试/提交证据，记录严重级别、复现步骤、影响范围、责任批次和复测结果。
- 所有修复在独立 feature 分支和 PR 中完成；不直接推送 main。
- 只有最终 PR head 的必需 CI、数据库矩阵、安装兼容性及审查全部通过才允许合并。
- 审计和测试不得连接生产数据库、生产支付凭据或真实资金环境；不得在审计工作流中部署或执行迁移。
- Provider、币种、汇率、退款和会计规则必须以官方规范及财务批准为依据，禁止猜测。

## 1. 全仓库功能盘点

每次审计先从当前代码动态生成清单，并与下列业务域逐项核对。对每项记录：前端入口、后端 API/Socket、服务层、数据库表/迁移、权限、审计事件、自动化测试、手工验收证据、状态和未决风险。

| 业务域 | 必须检查的功能边界 |
|---|---|
| 登录与身份 | 登录/登出、密码与会话、过期/撤销、账号状态、暴力尝试保护 |
| 组织与租户 | 平台/商户/门店边界、成员归属、跨租户和跨门店访问拒绝 |
| RBAC 与管理后台 | 页面与 API 权限一致、角色变更、越权调用、敏感操作二次确认 |
| 菜单与商品 | 分类、商品、规格、价格、可售状态、图片和多语言 |
| 桌台与点餐 | 桌台状态、二维码、购物车、订单创建、重复提交和边界输入 |
| 收银与支付 | 收款状态机、现金/扫码/第三方支付、回调重放、对账和失败恢复 |
| 订单与退款 | 订单状态转换、部分/全额退款、并发退款、金额语义和库存/销售统计 |
| 厨房与服务员 | 订单派单、制作状态、状态广播、断线重连和重复事件 |
| 外卖与骑手 | 配送单、接单/拒单/改派、客户追踪、位置权限、取消和退款联动 |
| 财务 Ledger | 账本写入边界、借贷平衡、幂等、原币精度、不可逆分录和导出 |
| 银行对账 | 流水导入、匹配建议、人工确认/拒绝/释放/重分配、异常分类、每日汇总 |
| 财务月结 | 期间锁定、准备度、Maker-Checker、并发、重试和审计历史 |
| 异常与 SLA | 案件分类、分派、备注、解决、提醒去重、时间窗口和历史 |
| 通知与集成 | Telegram/邮件/Socket/队列、重试、死信、重复通知和凭据保护 |
| 文件与导出 | 上传校验、路径安全、访问控制、CSV 公式注入、导出审计和备份恢复 |
| 系统配置与运维 | 配置校验、日志脱敏、健康检查、安装/升级/回滚、备份恢复 |
| 多语言与前端资源 | locale 键完整性、硬编码文案、构建产物同步、页面资源引用 |

若当前代码出现新业务域，必须新增到清单，不得强行归入“不适用”。

## 2. 每个功能的审计检查表

每个业务域都必须检查以下维度；不适用项需写明理由。

1. **入口与完整性**：页面按钮、表单、API、Socket 事件是否都有真实处理逻辑；是否存在空按钮、死路由、未接入页面、未使用模块或重复接口。
2. **业务状态机**：合法状态、非法跳转、终态、取消/退款/重试、并发竞争及补偿流程。
3. **身份与权限**：未登录、权限不足、停用账号、过期会话、伪造 actor/tenant/store ID、资源 ID 猜测。
4. **隔离边界**：商户、门店、用户、订单、流水、Ledger、文件、导出、缓存和异步任务均使用可信认证上下文。
5. **数据与事务**：约束、外键、唯一索引、锁顺序、事务边界、回滚、幂等键、重复请求及并发。
6. **迁移兼容**：新库安装、旧库升级、已填充数据、迁移重复执行、错误同名索引/字段、升级中断及回滚；禁止只验证 CREATE TABLE IF NOT EXISTS。
7. **审计与隐私**：操作者、时间、理由、前后状态、关联 ID、不可变历史；敏感信息/令牌/个人资料不得进入日志或报告。
8. **金额与数据精度**：原币隔离、整数最小货币单位、安全整数边界、舍入/汇率依据；不允许隐式币种转换。
9. **可靠性**：超时、重试、消息乱序、重复投递、断线、缓存失效、部分失败和恢复。
10. **性能与容量**：关键查询 EXPLAIN、分页稳定性、N+1、批量上限、索引、并发与目标容量。
11. **前端体验**：加载/空/错误/权限/网络状态、输入验证、移动端布局、可访问性和多语言。
12. **可运维性**：日志、指标、告警、健康检查、安装说明、配置示例、备份恢复及故障排查。

## 3. 自动化审计与测试层级

- 静态层：JavaScript、Shell、Python 语法；既有 scripts/audit-code.py；重复路由/函数报告 scripts/code-audit.py；多语言报告 scripts/i18n-audit.py。
- 单元层：每条业务规则至少覆盖正常、边界、拒绝、重复/幂等、异常路径。
- API/权限层：逐条注册路由盘点，验证未授权、跨租户、跨门店、伪造身份及资源 ID 越权。
- 数据库层：MySQL 8.4 与 MariaDB 10.11/11.4/11.8/12.3；真实事务、行锁、唯一约束、回滚、迁移重跑、历史数据保留。
- 端到端层：按业务旅程串联前端/API/数据库/异步事件；至少覆盖成功、失败、重试、并发和恢复。
- 交付层：依赖安全审计、安装兼容性、构建产物、备份恢复、文档与部署配置核对。

自动化报告是线索而不是最终结论。正则扫描无法证明权限或业务正确；必须由路由级测试、真实数据库测试和人工业务审查补足。报告中的误报必须有可复核的豁免理由、范围和复查日期。

## 4. 缺陷等级与处置

- **P0 阻断**：资金/账本错误、跨租户数据泄漏、认证绕过、数据丢失、生产密钥泄漏。立即停止发布；修复并完成回归和安全复审。
- **P1 严重**：核心业务无法完成、重复扣款/退款、权限绕过、迁移破坏历史数据、审计链失效。不得合并相关功能。
- **P2 一般**：局部功能错误、可靠性/性能明显退化、关键流程缺少测试。建立独立修复 PR 和验收条件。
- **P3 轻微**：文案、布局、低风险可用性问题。登记并安排修复，不得隐藏或伪装为已完成。

每个缺陷必须记录：编号、等级、模块、证据链接、复现、预期/实际、影响、根因、修复 PR、回归测试、最终状态。

## 5. 财务与支付特殊保护

- 自动匹配只生成建议，不确认收款、不改订单、不自动退款、不生成正式会计分录。
- 每次审核状态变更必须具备权限校验、可信租户上下文、事务/行锁、唯一约束、幂等和不可变审计。
- 退款金额语义不得在无批准情况下更改；分类退款异常不得改写原始流水金额。
- ABA PayWay、Bakong 或其他 Provider 的回调/验签、字段、币种映射、账户映射和会计科目必须来自官方规范、商户 Sandbox 及财务批准。
- 测试只使用合成数据和隔离数据库，不使用真实资金或生产凭据。

## 6. 每轮审计交付物

每轮产生并归档：
1. 基线 SHA、执行时间、审计范围和工具版本。
2. 功能清单及每项维度状态（通过/失败/未覆盖/不适用）。
3. 静态扫描、测试、数据库矩阵、安装兼容性和安全报告。
4. 缺陷清单（含严重级别、证据、负责人/修复 PR）。
5. 已修复项目的最终 PR head、CI run、测试结果和合并 SHA。
6. 未覆盖项、Provider 阻断项、风险接受人和下次复审日期。

不能以“测试全部通过”推断所有功能均已审计；未覆盖必须明确列出。

## 7. 合并与发布门禁

- 以最新 main 为基线创建独立分支；小批次 PR，避免混合无关业务。
- 每个 PR 先跑最终 head 的全部必需 CI、MySQL/MariaDB 矩阵和安装兼容性；失败必须修复并重跑。
- 审查最终 head，不采信旧提交的绿色检查；所有阻断 Review Thread 必须解决。
- 迁移必须在隔离旧库快照/合成数据上验证；本审计工作流不得对生产执行迁移或部署。
- 只有依赖关系正确、审查无阻断、所有必需检查成功才合并；否则保持 PR 开放并报告阻断。
- 合并后复验 main 的 CI。生产部署和真实 Provider 启用是独立审批流程，不属于本审计 PR 的自动动作。

## 8. 当前已存在的自动化基线

当前仓库 .github/workflows/ci.yml 已执行 JavaScript/Shell/Python 语法检查、scripts/audit-code.py、严格多语言检查、完整 npm test、生产依赖审计，以及 MySQL 8.4 和 MariaDB 四版本的财务集成/备份恢复测试。

仓库 .github/workflows/full-system-audit.yml 每日 02:00 UTC（柬埔寨时间 09:00）执行全系统自动审计，同时支持手动触发、针对 main 的 Pull Request 审计，以及每次提交进入 main 后的 push 审计。审计报告会在 audit-metadata.txt 中记录被审计的 commit SHA、ref、触发事件、run ID 和 run attempt；验收时必须核对该 SHA 与目标 main/PR head 完全一致，不得引用旧提交的报告。工作流归档静态检查、重复路由/函数和多语言扫描报告，并执行 MySQL/MariaDB 数据库矩阵；现有安装兼容性工作流仍作为独立门禁。审计清单的人工业务验收仍需逐模块完成，不能由工作流代替。
